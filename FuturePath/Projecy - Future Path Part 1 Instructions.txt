Future Path – Systems Design Specification Requirements

Purpose of the Design Phase

The analysis of the Future Path Student Advising System has been completed and the system
requirements are provided in the accompanying case study and test data specification.

Before development begins, each project team must complete a Systems Design Specification for
Future Path. The purpose of the design specification is to translate the system requirements into a
detailed technical design that will guide the development of the application.

The design must be based on the requirements contained in the Future Path case study. The final
system must be implemented as a standalone Windows Forms application, use a local relational
database, and follow a three-tier architecture consisting of a Presentation Layer, Business Logic Layer
and Data Layer.

Once the design phase has been completed, project teams will use their approved design to develop
Future Path. The completed system will subsequently be demonstrated and assessed.

1. Introduction

1.1 Overview of the Specification

Provide a brief overview of the purpose of the Systems Design Specification and explain how it will
guide the development of Future Path.

1.2 Context and Scope of the System

Briefly describe:

    •   the purpose of Future Path;
    •   the problem the system addresses;
    •   the intended users of the system;
    •   the major functionality that will be provided; and
    •   what is within and outside the scope of the current project.

The description should be consistent with the Future Path case study and should not introduce major
new functionality that is outside the stated project scope.

1.3 Design Assumptions and Constraints

Identify the assumptions and constraints that influence the design of the system.

At minimum, the specification must acknowledge that Future Path:

    •   must be implemented as a standalone Windows Forms application;
    •   must use a local relational database;
    •   must follow a three-tier architecture;
    •   must operate without a web server or cloud platform;
    •   must not connect to ChatGPT, Gemini, Copilot, online APIs or other external AI services;
    •   must implement its recommendation functionality using locally stored business rules, scoring
        and database data; and
    •   must implement appropriate authentication and role-based access for Career Advisors and
        System Administrators.

Any additional design assumptions made by the project team must be clearly stated.

2. User Interface and Dialogue Design

The project team must design the user interface for Future Path before development begins.

The interface design must demonstrate how users will navigate through the system and interact with
its major functions.

2.1 Interface Flow Diagram

Provide an interface flow/navigation diagram showing the relationships between the major screens
or forms in Future Path.

The diagram should indicate how users move between the main areas of the system.

The interface flow should accommodate the different functionality available to:

    •   Learners;
    •   Career Advisors; and
    •   System Administrators.

2.2 Screen Standards

Define the interface standards that will be applied consistently throughout the application.

These may include:

    •   form layout and positioning;
    •   navigation conventions;
    •   button placement and naming;
    •   fonts and headings;
    •   field labels;
    •   use of colours;
    •   error and confirmation messages;
    •   required-field indicators;
    •   data-entry conventions; and
    •   accessibility and usability considerations.

The standards should promote a consistent and user-friendly Windows Forms application.
2.3 Detailed Screen Designs

Provide detailed screen layouts or mock-ups for the major Future Path screens.

At minimum, the designs must show screens that support the following functionality:

   •   learner profile capture;
   •   subject and mark capture;
   •   interest questionnaire;
   •   faculty and degree programme selection;
   •   eligibility and recommendation results;
   •   alternative programme recommendations;
   •   funding information;
   •   advisory summary;
   •   Career Advisor functionality;
   •   Administrator login and maintenance functionality; and
   •   report selection and generation.

Each screen design must identify the important data elements and controls that will appear on the
screen.

Examples include:

   •   text boxes;
   •   labels;
   •   combo boxes;
   •   radio buttons;
   •   check boxes;
   •   date controls;
   •   grids;
   •   buttons; and
   •   validation or advisory messages.

The design must also indicate which information is entered by the user and which information is
retrieved, calculated or generated by the system.

3. Design Sequence Diagrams

The project team must create at least two Design Sequence Diagrams for important Future Path
processes.

The following two processes must be modelled:

   1. Check Degree Eligibility and Generate an Advisory Outcome
   2. Generate Alternative Degree Recommendations

The sequence diagrams must show the interaction between the relevant components of the three-
tier architecture.
Where appropriate, the diagrams should show interaction between:

   •   the Windows Forms user interface;
   •   Presentation Layer objects;
   •   Business Logic Layer objects;
   •   Data Layer objects; and
   •   the database.

The diagrams must demonstrate the order in which messages or method calls occur and how
information moves through the system to complete the selected process.

The diagrams should represent the design of the proposed system, rather than simply reproducing
the business process described in the case study.

4. Design Class Diagram

Provide a Design Class Diagram for Future Path.

The class diagram must represent the classes required to support the proposed system design and
should include, where appropriate:

   •   class names;
   •   attributes;
   •   data types;
   •   methods/operations;
   •   visibility;
   •   associations;
   •   multiplicities;
   •   inheritance, where applicable; and
   •   other relevant relationships between classes.

The class design should support the required three-tier architecture and the functionality described
in the Future Path case study.

The project team must demonstrate a clear relationship between the classes included in the design
and the functionality that will subsequently be implemented.

5. Entity Relationship Diagram

Provide a complete Entity Relationship Diagram (ERD) for the Future Path database.

The ERD must show:

   •   entities;
   •   primary keys;
   •   foreign keys;
   •   relevant attributes;
   •   relationships; and
   •   relationship cardinalities.
The database design must support the data requirements specified in the Future Path case study and
test data specification.

The database must be normalised to Third Normal Form (3NF).

The project team is responsible for determining the final database structure. The entities identified in
the case study provide guidance regarding the information that the system must store but do not
remove the team's responsibility to design an appropriate relational database.

6. Report Design

Future Path must provide at least three meaningful reports.

The Systems Design Specification must contain the design of the reports that will subsequently be
implemented.

At minimum, the following reporting requirements from the case study must be addressed:

    1. Learner Advisory Summary Report
    2. Degree Interest and Eligibility Report
    3. Learners Not Currently Eligible Exception Report

6.1 Output Requirements

For each report, specify:

    •   report name;
    •   purpose;
    •   intended user;
    •   data included in the report;
    •   source of the data;
    •   selection/filtering criteria;
    •   calculations or summaries required;
    •   sort order, where applicable;
    •   frequency or circumstances in which the report is generated; and
    •   whether the report is displayed, printed, saved or exported.

6.2 Report Layout

Provide a proposed layout/mock-up for each report.

The layout should indicate:

    •   report title;
    •   headings;
    •   data fields;
    •   grouping;
    •   totals or summary information, where applicable;
    •   date generated;
    •   page information, where appropriate; and
    •   any required advisory disclaimer.
The Learner Advisory Summary must be designed so that it can be exported or saved for sharing with
a learner, parent, teacher or Career Advisor.

7. Input and Output Standards and Controls

The specification must identify the controls that will be implemented to ensure that Future Path
processes accurate, valid and appropriate data.

7.1 Input Standards

Define standards for data captured by users, including appropriate formats, required fields and data-
entry conventions.

7.2 Built-in Validation

Identify the validation that will be implemented within the user interface and business logic.

Examples include:

    •   marks must be between 0 and 100;
    •   required information may not be left blank;
    •   duplicate subjects may not be captured for the same learner/advisory session;
    •   valid dates must be entered;
    •   a degree must be associated with a valid faculty; and
    •   only valid funding types may be selected.

7.3 Input Integrity Controls

Describe the controls that will be used to protect the accuracy and integrity of data entered into the
system.

These may include:

    •   range checks;
    •   format checks;
    •   lookup lists;
    •   duplicate checks;
    •   required-field validation;
    •   referential integrity; and
    •   confirmation messages.

7.4 Output Integrity Controls

Describe the controls that will ensure that outputs produced by Future Path are accurate, meaningful
and appropriately presented.

These must consider requirements such as:

    •   providing reasons for advisory outcomes;
    •   displaying required disclaimers;
    •   identifying the date on which reports were generated;
    •   excluding inactive degree programmes or outdated funding options;
    •   ensuring that users only access reports appropriate to their role; and
    •   identifying sample funding or programme information that may require verification.

8. Security and Access Design

Describe how access to Future Path will be controlled.

The design must show how the system will distinguish between the different user roles.

At minimum:

    •   Career Advisors must authenticate before accessing Career Advisor functionality;
    •   System Administrators must authenticate before accessing administrative functionality;
    •   Career Advisors must not be permitted to perform Administrator-only maintenance functions;
    •   System Administrators must be responsible for maintaining programme requirements,
        funding information, interest questionnaire information and other reference data; and
    •   appropriate role-based restrictions must be implemented.

The specification should indicate how the proposed interface and class/database designs support
these access requirements.

9. Implementation Plan

Provide a brief implementation plan explaining how the project team intends to move from the
approved system design to the completed Future Path application.

The plan should identify:

    •   the major development activities;
    •   the order in which components will be developed;
    •   database development;
    •   user-interface development;
    •   business-logic development;
    •   integration of the three tiers;
    •   report development;
    •   testing;
    •   responsibilities allocated to project team members; and
    •   key milestones.

The implementation plan should demonstrate that the team has a realistic approach for completing
the system within the available project period.
10. Test Plan

Before development begins, the project team must identify how the completed Future Path system
will be tested.

10.1 Test Environment

Describe the proposed environment in which Future Path will be developed and tested, including
relevant software, database and application requirements.

10.2 Areas to be Tested

Identify the major functionality that must be tested.

At minimum, testing must cover:

    •   learner profile creation;
    •   subject and mark capture;
    •   validation;
    •   interest questionnaire processing;
    •   degree eligibility checking;
    •   advisory outcomes;
    •   alternative degree recommendations;
    •   funding information;
    •   advisory report generation/export;
    •   Career Advisor functionality;
    •   Administrator functionality;
    •   authentication and role-based access; and
    •   required reports.

10.3 Test Approach

Explain the approach that will be followed when testing the system.

Testing should include both:

    •   successful/valid scenarios; and
    •   unsuccessful, invalid or exception scenarios.

Students must consider the test data and expected outcomes provided in Part B of the Future Path
case study.

10.4 Test Cases

The detailed test cases used to test the completed application do not have to be included in the
Systems Design Specification.
However, project teams must prepare the required test cases during development. These test cases
must be available and used during the final system demonstration to show that Future Path performs
according to the specified requirements.

At minimum, the demonstration must include the test scenarios required in Part B of the case study.
11. Relationship Between Design and Development

The Systems Design Specification represents the proposed design of Future Path.

Once the design phase has been completed, project teams must develop the system according to their
submitted design.

The completed system should therefore correspond with the:

    •   interface designs;
    •   class design;
    •   database design;
    •   sequence diagrams;
    •   report designs;
    •   validation and control design;
    •   access-control design; and
    •   other technical decisions documented in the Systems Design Specification.

Where a project team makes a significant change to the design during development, the team must
be able to explain and justify the change during the final demonstration.

The final assessment will therefore consider not only whether Future Path functions correctly, but also
whether the developed application appropriately reflects the system design produced by the project
team.
